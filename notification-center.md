# Pattern: Notification center

A **new platform surface** — it does not exist in the product yet. Drafted 11 Sep 2026 from a feature brief by Rajat Garg plus one reference mock (a Figma-style notifications popover); unlike the observed page patterns this is a proposal, so everything is either grounded in an existing pattern, cited to a guideline, matched to the reference mock, or flagged `[proposed]`. Where this pattern deliberately departs from the reference mock, §6 records it. Revised later the same day from Rajat's review: `LTTabNav` replaces `LTUnderlineNav` inside the panel (§5, decision 3), the short time formats are a panel-local exception with no guideline changes (§5, decision 7), and lazy loading rides the existing feed idiom rather than a rule amendment (§3.6).

Every component and prop below was read from `COMPONENTS.md`. Nothing is invented. Structured prop shapes are marked `TBD` with the Storybook story that shows the real shape.

**Shell surface, the fourth.** Like the sidebar, the top bar and the modal (`design-context/patterns/README.md`, Shell patterns), this is patterned once and every product inherits it. Two pieces: a **bell icon button** in the top bar's right cluster, and the **notification panel** it opens. The bell's placement inside the bar is recorded in `../design-context/patterns/topbar.md` (amended 11 Sep 2026); everything else about it lives here.

---

## 1. What this is

The platform's in-app notification center. Every LambdaTest product — Test Manager, KaneAI, SmartUI, HyperExecute, Automation, Real Time / App Testing and the rest — is desktop web, org-scoped, and multi-user, but nothing today tells a user when another user or the system touches their work: their files, projects, test cases, test runs, HyperExecute jobs, automation builds. This closes that gap with one bell in every product's top bar and one panel behind it.

- **Org-scoped.** A notification is generated by activity inside the user's own organisation — another member's action, or a system outcome on the user's own work. There is no cross-org traffic, so rows do not carry an org name (§6, delta 3).
- **Cross-product.** One feed for the whole platform. The product a notification came from is row metadata, not a separate inbox.
- **14-day window.** The feed holds the last 14 days, both tabs, and the bell's unread count covers the same window. Older notifications are gone, and the end of the feed says so (§3.6).
- **No settings, no search, v1.** Deliberate scope cuts from the brief — see the deliberately-absent list in §2.

What it is **not**:

- **Not notification *messaging*.** `guidelines/notification-messaging.md` governs feedback to the acting user about their own in-flight action (LTFlash, LTInlineMessage, LTToast, LTModal) — you did a thing, the UI responds now, next to the thing. This panel is the opposite end: activity by *someone else* (or the system, later) reaching you where you aren't looking. A surface never swaps one for the other: an import you start shows progress via Project Actions and messaging components; the *notification* that it finished goes to the people it affects.
- **Not an audit log.** The SmartUI Activity specs and `project-actions-listing.md` answer "what happened in this project, exhaustively". Notifications are the curated subset addressed to *you* — relevance, not completeness.
- **Not announcements.** The existing announcements icon button in some product bars carries LambdaTest-the-company's product news. Different author, different audience, different button (open question 9).

### 1.1 The notification model

One notification is one event addressed to one user. Fields, all of which appear in §3.4's anatomy:

| Field | Notes |
|---|---|
| `id`, `createdAt`, `read` | `read` drives the tab split, the dot, the badge and the counter |
| `actor` | An org member (name → initials avatar, `mock-data.md` rules) **or the system** (open question 4) |
| `title` | Rich text: actor + verb phrase + object, object bold (§3.4) |
| `product` | Display name as the patterns spell it: Test Manager · KaneAI · SmartUI · HyperExecute · Automation · Real Time |
| `href` | The entity the notification is about; opening the row navigates there (destinations per event type — open question 8) |
| `actions?` | At most two: one primary + one secondary (§3.4) |
| `attachment?` | At most one linked artifact, e.g. a report file (§3.4) |

### 1.2 Representative events — a seed, not a catalog

The brief names the entity families; the per-product event catalog (which events notify, whom, and with what destination) is product-team work that this pattern deliberately does not invent (open question 8). These rows exist so the anatomy can be exercised — every one uses an entity type that already exists in this repo's patterns:

| Product | Event | Title grammar | Extras |
|---|---|---|---|
| Test Manager | Invited to a project | `{Actor} invited you to project {project}` | Accept + Decline |
| Test Manager | Test run assigned | `{Actor} assigned you the test run {run}` | — |
| Test Manager | Bulk operation on your work (the `project-actions-listing.md` seven: import, export, move, copy, delete, automation, run execution) | `{Actor} moved 24 test cases to {destination}` | — |
| SmartUI | Screenshots approved / rejected | `{Actor} approved 12 screenshots in {project}` | — |
| HyperExecute | Job finished / failed | `HyperExecute job {job} failed` | System row |
| Automation | Build finished, report ready | `{Actor} shared the report {file}` | Attachment |
| KaneAI | Generation finished | `KaneAI finished generating {run}` | System row |

Titles are prose, so status words take their natural verb forms (`failed`, `succeeded`). The status *vocabularies* in `mock-data.md` still bind: a test run `passed`, a build `succeeded` (build status is only success/failure), and no verb outside those meanings gets invented for an outcome.

## 2. Component inventory

| Component | Role | Notes |
|---|---|---|
| `LTAnchoredOverlay` | The whole trigger-plus-panel assembly | "Overlay which will be attached to a button" — its own description. `anchorType="iconButton"`, `buttonVariant="outline"`, `ariaLabel`, `counterValue`, `align="end"`. How the bell icon and the panel body are supplied is undocumented — TBD → `ltanchoredoverlay--icon-button-anchor`, `--custom-component-anchor`. See open question 1 |
| `LTNotificationIndicator` | Unread count on the bell; unread dot on rows | `type="counter"` with `maxCount` (default 99) on the bell; `type="dot"` on rows. `variant="default"` both places. Positioning composition TBD → `ltnotificationindicator--counter-indicator`, `--dot-indicator` |
| `LTTabNav` | Unread / All tabs | `size="small"`, `ariaLabel="Notifications"`, `activeTab`, `onSelect`; `isLeadingSpaceRequired` already defaults `false`. `items` shape TBD → `lttabnav--tab-nav` |
| `LTCounterLabel` | The count in the Unread tab | Composed into the Unread tab's item — LTTabNav documents no counter of its own, and none of its four stories shows one. `scheme="secondary"` per the `guidelines/ltcounterlabel.md` default; omitted at zero. Whether `items` accepts a node: `lttabnav--tab-nav` |
| `LTText` | Panel heading, row title fragments, meta line, terminal row | Mixed-weight titles compose `as="span"` fragments: `SMALL_BOLD` for actor and object, `SMALL_REGULAR` for the verb phrase. Variant-to-role mapping is the known typography blocker (`guidelines/README.md` §3) |
| `LTAvatar` | Actor on each row | `initials`, `name`, `size={32}`, `type="circle"`. Initials rules per `mock-data.md` — always initials, never an image. System rows: open question 4 |
| `LTButton` | Mark all as read; row actions | Header: `variant="invisible"` `size="small"`. Rows: secondary `variant="default"` + primary `variant="primary"`, both `size="small"`, primary last, hard right (`guidelines/README.md` §7; `guidelines/ltbutton.md`) |
| `LTLink` | Attachment chip | Opens a document → link, not button, not tag (`guidelines/ltlink.md`; `guidelines/lttag.md` — tags are read-only). `size="small"`, `leadingIcon` = attachment glyph (icons.md, TO FILL) |
| `LTInlineMessage` | A row action that failed | `variant="error"` `size="small"`, adjacent to the buttons (`guidelines/notification-messaging.md`: feedback about one control sits next to it). Text mechanism undocumented — TBD → `ltinlinemessage--error` |
| `LTBlankSlate` | Empty states, one per tab | `heading`, `description`, `narrow`; Unread adds a switch-to-All action (§4) |
| `LTLoader` | First load; lazy-load row | `size="medium"` centred, then `size="small"` under the last row while the next page arrives (`guidelines/ltpagination.md` loader placement) |
| `LTFlash` | Panel failed to load | `variant="danger"`, inside the panel, one per surface max (`guidelines/README.md` §1) |
| `LTIconButton` | Fallback bell if the built-in anchor can't take a lucide icon | `icon={Bell}`, `ariaLabel`, `variant="outline"`, `size="medium"`, tooltip built in — see open question 1 |
| `LTBox`, `LTDivider` | Panel frame, row separators | `LTDivider` between rows, as on the listing feeds |

**Icons.** The bell is lucide `Bell` — specified in the brief, 11 Sep 2026, and added to the approved set in `icons.md`. The attachment glyph is named by intent only (paperclip) until its lucide name is verified there; **never guess an icon name** (`icons.md` hard rule).

**Deliberately absent:** an in-panel search (`LTInputBox`) and any notification settings entry — both cut by the brief, v1. `LTPagination` — the feed lazy-loads on scroll like its newest-first siblings (`hyperexecute-jobs-listing.md`), see §3.6. `LTUnderlineNav` — a page's primary, URL-backed tab layer (`guidelines/ltunderlinenav.md`); the host page already carries one, and an overlay's tabs are the second, URL-less layer that same guideline assigns to LTTabNav (Rajat, 11 Sep 2026 — §5, decision 3). `LTPopover` — scoped to onboarding tips and explicitly never for anything critical (`guidelines/ltpopover.md`); this panel is a working surface, not a tip. `LTActionMenu` — menus may contain no buttons or inputs (`guidelines/ltactionmenu.md`), and rows carry buttons. `LTDrawer`/`LTModal` — a notification check is a glance, not a task; nothing may block or cover the page. `LTTag` on rows — the event type is legible from the sentence; a tag would restate it (and the attachment is a link, not a tag). `LTTimeline` — the feed is flat, not day-grouped (§5, decision 6). Relative timestamps — §5, decision 7.

## 3. Structure

### 3.1 The bell, in the top bar

Placement, verbatim from the amended `topbar.md`: right cluster, **between the product icon buttons and the avatar**, constant across every product — quota modules and product buttons vary per product, the bell does not, so it sits with the other constants (avatar, `Upgrade Now`).

```jsx
import { Bell } from "lucide-react";
import { LTAnchoredOverlay } from "@lambdatestincprivate/lt-components";

{/* The one assembly in the library built for this: an LTIconButton anchor
    with a counter, opening an attached overlay. outline + medium to match
    the product buttons beside it (topbar.md; the outline usage rule in
    guidelines/lticonbutton.md is still open — the bar's precedent decides).

    counterValue = unread in the last 14 days; null at zero so nothing
    renders. Cap and rendered form ("99+") come from the counter treatment —
    LTNotificationIndicator maxCount default 99 — verify which piece renders
    it: open question 2.

    The accessible name carries the count (primer-dos-donts/underline-nav.md
    a11y rule, applied to the same counter-on-a-control shape), and the
    LTIconButton tooltip names the button on hover and focus (lticonbutton.md).

    How the Bell glyph reaches the anchor is undocumented — no icon prop in
    the manifest. TBD → ltanchoredoverlay--icon-button-anchor. If the anchor
    cannot take a lucide icon, fall back to composing LTIconButton +
    LTNotificationIndicator type="counter" as a custom anchor
    (ltanchoredoverlay--custom-component-anchor), and if that also fails,
    the panel positions itself under a plain LTIconButton — custom, flagged,
    per the build-custom rule in guidelines/README.md §10. */}
<LTAnchoredOverlay
  anchorType="iconButton"
  buttonVariant="outline"
  ariaLabel={unread > 0 ? `Notifications, ${unread} unread` : "Notifications"}
  counterValue={unread > 0 ? unread : null}
  align="end"
/>
```

Behaviour the trigger owes, whoever renders it:

- The badge updates live while the page is open, panel closed or not — the badge is the product's pulse, an ambient signal (transport: open question 10).
- Badge hidden at zero. A bare zero is noise; the empty state inside the panel says "caught up" instead.
- Opening the panel does **not** mark anything read (§3.5). The badge drops as rows are read, not on open.
- `aria-expanded` reflects open state; what LTAnchoredOverlay provides vs. what FE adds is part of open question 1.

### 3.2 The panel frame

Opens below the bell, right-aligned to it — `align="end"`, outside-bottom (the `Side` enum exists on the component; which prop carries it is undocumented, same TBD).

- **Width 400px** — the middle step of the sanctioned side-pane scale, the "rows are cards with meta" tier (`guidelines/README.md` §2). Do not measure a new width.
- **Height is viewport-fixed** (brief): `height: calc(100vh − {bar height} − 8px − 16px)` — 8px gap under the bar `[proposed]`, 16px inset from the viewport bottom `[proposed]`, all multiples of 4. The bar-height token is still TBD in `topbar.md` §7; this calc inherits it symbolically. The panel does not grow or shrink with content; short content leaves empty surface below `[per the brief — fixed means fixed]`.
- **Internal split:** header and tabs are fixed; only the list region scrolls (`overflow-y: auto`). The scrollbar belongs to the list, never the whole panel, so the tabs stay reachable mid-feed.
- **Surface:** `canvas.overlay` background (`TOKENS.md`, `colorSchemes.light.colors.canvas`), 8px radius (the settled listing-container radius), elevation from the **`floating/*`** shadow family — "overlays and raised surfaces", `shadow-tokens-snippets.md`; exact tier `[proposed: floating-small, the dropdown-scale composite — confirm against the Figma overlay specs]`.
- **Dismiss:** Esc, click outside, and the bell itself (toggle). On close, focus returns to the bell. On open, focus moves into the panel; the panel is `role="dialog"` with `aria-label="Notifications"`, not modal — no page dimming, no focus trap. How much of this LTAnchoredOverlay ships vs. FE adds: open question 1. (The warning in `primer-dos-donts/popover.md` — Primer overlays may handle none of it — is why this is written down rather than assumed.)
- Navigating from a row closes the panel. In-panel actions (Accept, Mark all as read, tab switches) keep it open.

### 3.3 Header and tabs

```jsx
import { LTBox, LTText, LTButton, LTUnderlineNav } from "@lambdatestincprivate/lt-components";

<LTBox styles={{ display: "flex", alignItems: "center", justifyContent: "space-between", padding: "16px 16px 8px" }}>
  {/* Panel title. SUBHEADER_BOLD [structural — the variant-to-role mapping
      is the known typography blocker, guidelines/README.md §3]. */}
  <LTText as="h2" variant="SUBHEADER_BOLD" text="Notifications" />

  {/* Acts in-page → button, never a link (guidelines/ltlink.md boundary).
      invisible: minimal UI inside a compound surface (guidelines/ltbutton.md).
      Rendered only while unread > 0 [proposed]. loading while the bulk
      update runs (guidelines/README.md §7). On success: nothing — the
      emptied tab and the vanished badge are the message (success messaging
      is used sparingly, notification-messaging.md), but the state change
      must still reach screen readers (README §8), announced politely. */}
  {unread > 0 && (
    <LTButton variant="invisible" size="small" label="Mark all as read" onClick={() => {}} />
  )}
</LTBox>

{/* Two tabs, Unread default — the count is why the panel was opened, so it
    lands on what the count counts [proposed]. LTTabNav, not LTUnderlineNav:
    the underline nav is a page's primary, URL-backed tab layer, and the tab
    structure after that is LTTabNav's job (guidelines/ltunderlinenav.md) —
    an overlay's tabs are exactly that second, URL-less layer. §5 decision 3.

    Counter in the Unread tab: composed LTCounterLabel (scheme="secondary"),
    since LTTabNav documents no counter — whether `items` accepts a node is
    TBD → lttabnav--tab-nav. Omitted at zero, the project-actions convention.
    The count must be part of the tab's accessible name (the counter rule in
    primer-dos-donts/underline-nav.md, applied to the same shape).
    isLeadingSpaceRequired defaults false here — the 16px panel padding
    already provides the inset. */}
<LTBox styles={{ padding: "0 16px" }}>
  <LTTabNav ariaLabel="Notifications" size="small" items={[]}
    activeTab="unread" onSelect={() => {}} />
</LTBox>
```

Tab behaviour: **Unread** holds unread only, newest first; a row opened from it is marked read and leaves the tab. **All** holds everything in the window, read and unread interleaved, newest first; read rows keep their place and lose the dot. Switching tabs resets scroll to the top `[proposed]`.

### 3.4 The notification row

Anatomy, left to right: avatar · text block (title line, then meta line) · unread dot. Below the text block, when present: the action pair, or the attachment, or a resolved-action note. The reference mock's row, re-cast in LT parts.

```jsx
import {
  LTBox, LTText, LTAvatar, LTButton, LTLink, LTNotificationIndicator, LTDivider,
} from "@lambdatestincprivate/lt-components";

function NotificationRow({ n }) {
  return (
    /* Unread rows sit on the canvas.subtle tint, read rows on canvas.default
       [proposed — both tokens in TOKENS.md colorSchemes.light]; hover is a
       grey fill (fill alone reads as hover — the selection rule in
       guidelines/README.md §1, inverted deliberately: this IS hover).
       Never colour alone for unread: tint + dot + the word "Unread" in the
       row's accessible name (README §9). */
    <LTBox styles={{ display: "flex", gap: "12px", padding: "12px 16px" }}>

      {/* Human actor: initials per mock-data.md (two-word → RS, three-word →
          MB, single-word → one letter). System rows: open question 4. */}
      <LTAvatar initials={n.actor.initials} name={n.actor.name} size={32} type="circle" />

      <LTBox styles={{ flex: "1 1 auto", minWidth: 0 }}>
        {/* Title: mixed weights compose as spans — actor and object SMALL_BOLD,
            verb phrase SMALL_REGULAR. The whole text block is the row's one
            navigation target: a link to n.href (links navigate —
            guidelines/ltlink.md), which also marks the row read. The full-row
            hit area extends that link [proposed]; the buttons and attachment
            below stay separate tab stops, never nested inside it.
            Two-line clamp, then ellipsis: long run/build names must survive —
            the UUID build shape is the stress case (mock-data.md). */}
        <LTText as="span" variant="SMALL_BOLD" text={n.actor.name} />{" "}
        <LTText as="span" variant="SMALL_REGULAR" text={n.verbPhrase} />{" "}
        <LTText as="span" variant="SMALL_BOLD" text={n.object} />

        {/* Meta: time · product. Today → "2:34 PM"; yesterday and older →
            "Sep 10". Formats and their mock-data.md collision: §5 decision 7.
            Viewer's local time, no timezone suffix (brief). Muted treatment
            [structural — typography blocker]. */}
        <LTText as="p" variant="SMALL_REGULAR" text={`${n.time} · ${n.product}`}
          style={{ marginTop: "4px" }} />

        {/* Slot, at most one of: */}

        {/* a) Action pair. Secondary (default) left, primary right, hard
              right per the footer-order rule (guidelines/README.md §7) —
              which is also the brief's requirement, verbatim. Both small.
              Clicked button takes loading; on failure an LTInlineMessage
              variant="error" size="small" renders adjacent, below the pair
              (notification-messaging.md: feedback next to its control; text
              mechanism TBD → ltinlinemessage--error). On success the pair is
              replaced by a muted SMALL_REGULAR note — "Accepted" /
              "Declined" [proposed] — the row remains as a record. */}
        {n.actions && (
          <LTBox styles={{ display: "flex", justifyContent: "flex-end", gap: "8px", marginTop: "8px" }}>
            <LTButton variant="default" size="small" label={n.actions.secondary} onClick={() => {}} />
            <LTButton variant="primary" size="small" label={n.actions.primary} onClick={() => {}} />
          </LTBox>
        )}

        {/* b) Attachment. Opens a document → LTLink, never LTTag (tags are
              read-only metadata, guidelines/lttag.md) and never a button.
              Leading glyph: paperclip by intent — lucide name TO FILL in
              icons.md before build. Link text = the file name, end-truncated
              with a tooltip carrying the full string. */}
        {n.attachment && (
          <LTBox styles={{ marginTop: "8px" }}>
            <LTLink size="small" href={n.attachment.href} label={n.attachment.name}
              leadingIcon={null /* paperclip — icons.md */} />
          </LTBox>
        )}
      </LTBox>

      {/* Unread dot. Not interactive in v1 — an 8px-scale dot can't meet the
          24px target floor (README §9); marking read is done by opening the
          row or Mark all as read. A per-row control is open question 6.
          Hidden on read rows. */}
      {!n.read && <LTNotificationIndicator type="dot" variant="default" size="small" />}
    </LTBox>
  );
}
```

`LTDivider` between rows, none after the last — the listing-feed treatment.

### 3.5 Reading and live behaviour

- **Read = opened.** Opening a row (navigating to its entity) marks it read. So does Mark all as read. Nothing else does — not opening the panel, not scrolling past.
- **Acting is not reading, formally:** Accept/Decline resolves the *action*; the row it sits in also becomes read `[proposed — one gesture should not demand two]`.
- **Arrivals while open** insert at the top; badge and tab counter tick up. The list announces politely (`aria-live="polite"` on the list region `[proposed]`); scroll position must not jump for a reader mid-feed.
- The bell badge, the Unread counter and the Unread tab's contents are three views of one number — they may never disagree.

### 3.6 The feed: window, lazy loading, virtualization

- **Window: 14 days.** Both tabs. When the feed's end is reached, a terminal row closes it — `Showing the last 14 days.` — centred, muted, `SMALL_REGULAR` `[proposed copy — one line, states the boundary, no negation, README §8]`.
- **Lazy loading.** First open fetches 20 — the default page size for every list (`guidelines/ltpagination.md`) — and each scroll toward the bottom fetches the next 20, triggered ~200px before the end `[proposed]`. The in-flight page shows an `LTLoader size="small"` row under the last row, exactly the mid-feed loader treatment already settled for feeds; never a full-panel spinner after first load.
- **Virtualized rendering** (brief): rows outside the viewport unmount; the two week's worth of an active org must not sit in the DOM. Constraint for FE: row heights vary (actions, attachments, two-line titles), so the windowing must measure, not assume. Library is FE's choice — nothing in lt-components covers this; custom and flagged, per `guidelines/README.md` §10.
- **No pagination, and no new rule needed.** The panel is the same newest-first, reverse-chronological feed the product already ships: `hyperexecute-jobs-listing.md` (and its Automation siblings) sort the most recent item to the top, never paginate, and load the next chunk under a small foot loader as the user reaches the bottom. The notification feed shares that sorting order and inherits the idiom as-is (Rajat, 11 Sep 2026); the only difference is presentation — flat rows instead of day groups (decision 6).
- Lazy-loaded rows append without moving focus; the loader row is what screen readers hear, politely, while a page is in flight.

## 4. States

Every panel needs empty, loading and error designed (`guidelines/README.md` §1). Here the empties are per-tab:

```jsx
/* Empty, Unread tab — the good state. One line, one action (README §8);
   the action switches tabs in place, so it is a button, not a link.
   Visual: the Bell glyph, already approved in icons.md — no new icon.
   [proposed copy] */
<LTBlankSlate
  visual={null /* Bell */}
  heading="You're all caught up"
  description="New notifications from your organisation appear here."
  primaryAction={<LTButton variant="default" size="small" label="View all notifications" onClick={() => {}} />}
  narrow
/>

/* Empty, All tab — nothing in 14 days. No action, deliberately: there is
   nothing to do here, and a CTA that navigates away from an overlay is
   worse than none (the project-actions precedent, decision 5). [proposed copy] */
<LTBlankSlate
  visual={null /* Bell */}
  heading="No notifications yet"
  description="Activity that involves you — runs, builds, shares, invites — shows up here."
  narrow
/>

/* Loading, first open. Centred in the list region. */
<LTBox styles={{ display: "flex", justifyContent: "center", padding: "48px 0" }}>
  <LTLoader size="medium" />
</LTBox>

/* Lazy-load, mid-feed — under the last row (§3.6). */
<LTBox styles={{ display: "flex", justifyContent: "center", padding: "16px 0" }}>
  <LTLoader size="small" />
</LTBox>

/* Error — the feed itself failed. Inside the panel, below the tabs; one
   LTFlash per surface, maximum. Same copy shape as the project-actions
   feed error, for consistency. */
<LTFlash variant="danger" text="We could not load notifications. Retry, or check your connection." fullBorder />
```

A failed row *action* (Accept that 500s) is a row state — the adjacent `LTInlineMessage` in §3.4 — never a panel-level banner.

## 5. Design decisions

The calls made in this proposal, with the rejected alternative each time. All 11 Sep 2026.

1. **`LTAnchoredOverlay` is the container — not `LTPopover`, not a menu, not a drawer.** LTPopover is scoped to onboarding tips ("light onboarding and instructions", never anything critical — `guidelines/ltpopover.md`); LTActionMenu forbids buttons and inputs inside it (`guidelines/ltactionmenu.md`); LTDrawer/LTModal block or cover the page for what is a glance. LTAnchoredOverlay's own description — an overlay attached to a button, with an iconButton anchor type and a counter — is this feature's shape. It has no guideline file yet; writing one is in the ship checklist.

2. **The unread badge is `LTNotificationIndicator`, not `LTCounterLabel`.** The counter-label guideline draws this exact line: a counter never stands alone and always sits beside text naming what it counts — and routes indicator duty to LTNotificationIndicator explicitly. On the bell the number stands alone (the accessible name carries the context); in the Unread tab the count sits beside its label, so *that* one is the LTCounterLabel. Each component where its own rule puts it.

3. **`LTTabNav` for the tabs — the second tab layer, which is what an overlay's tabs are.** First drafted as `LTUnderlineNav`; Rajat's review (11 Sep 2026) corrected it, and the guidelines agree once the layering is read right: `guidelines/ltunderlinenav.md` scopes LTUnderlineNav to a page's primary, URL-backed tab structure — one per page, every tab its own URL — and assigns any further tab structure on the same page to **LTTabNav**. The host page has already spent its primary layer (and its URLs); the panel's Unread / All is an in-surface switch, so it takes the second-layer component. This is also the first concrete data point for the unresolved LTUnderlineNav-vs-LTTabNav relationship note in `primer-dos-donts/underline-nav.md`: overlay surfaces tab with LTTabNav.

4. **Unread is the default tab.** The user opened the panel because the badge showed a number; landing anywhere else puts a click between the pull and the payoff. At zero unread the tab shows the caught-up state with a one-click path to All (§4). `[proposed — the reference mock's default is its "Inbox", which conflates the two]`

5. **Opening the panel does not mark all read.** A glance at the badge's contents must be free: mass-marking on open destroys the unread list the user came to triage. Reading is per-row (open it) or explicit (Mark all as read). The alternative — auto-read on open, as some products do — trades away triage for a quieter badge, and is rejected.

6. **A flat feed — no day-group headings.** The reference mock is flat; per-row timestamps (brief) carry the day; and a 400px panel spends its height on rows, not headings. This departs from the day-grouped `LTTimeline` idiom of the full-page feeds deliberately — an overlay is a skim surface, not a page. If the panel ever grows day groups, the pagination exception in `ltpagination.md` already covers the grouped form.

7. **Absolute, short timestamps — the brief overrides two `mock-data.md` rules, recorded here.** The brief: today → `2:34 PM`, yesterday and older → `Sep 10`; no timezone handling, viewer-local. Against the conventions this collides three ways: (a) `mock-data.md` requires *relative* time under 30 days — this panel is absolute-only; (b) `MMM DD` without a year is a new format — safe only because the 14-day window makes a year ambiguity impossible, which is why it must not leak to any surface without such a window; (c) the brief's examples are unpadded (`2:34 PM`, `Jan 1`) where mock-data's formats are zero-padded (`07:33 AM`, `Sep 03`). This pattern follows the brief's examples as written — `2:34 PM`, `Sep 10`, unpadded — and Rajat's review (11 Sep 2026) settled the scope: **this is a use-case exception recorded here, and the existing format conventions stay untouched.** `mock-data.md` and the guidelines are not amended; every surface outside this panel keeps the standard formats, and nothing here is precedent for one.

8. **The meta line names the product, not the org.** The reference mock shows a workspace per row because Figma's inbox spans workspaces; this feed is org-scoped by definition (§1), so an org label would repeat the same value on every row. The product is the variable that helps ("which of my seven LambdaTest tabs is this about").

9. **Row actions: exactly the brief's shape, and it matches the house rule.** At most one primary and one secondary, primary to the right — the brief's requirement is `guidelines/README.md` §7's footer order verbatim (secondary → primary, primary hard right), both `small` per the brief. No third action, ever; a notification needing three actions is a page's job.

10. **The unread dot is not a button in v1.** The mock's dot invites click-to-toggle, but a dot-sized control breaks the 24×24 target floor (README §9) and an invisible toggle next to a navigating row invites misclicks. Marking read stays coarse (open the row, or mark all) until open question 6 decides a proper per-row control.

## 6. Deltas from the reference mock

Where this pattern deviates from the supplied screenshot, and why. (The mock is a Figma-style panel; it seeds the anatomy, the brief and the guidelines override it.)

1. **Initials avatars, never facial.** The mock's memoji/photo avatars → `LTAvatar` initials; LambdaTest org users have no facial avatars (brief), and `mock-data.md` bans avatar images outright.
2. **Tabs are Unread / All, not Inbox / General / Archived.** Per the brief. There is no archive concept in v1, and no third bucket.
3. **No settings gear.** The mock's header gear → omitted; there are no notification settings in v1 (brief).
4. **No presence dots on avatars.** The mock shows online-status dots; LambdaTest has no presence system, and inventing one for a panel would be scope by accident.
5. **Absolute times, not relative.** "36 mins ago" → "2:34 PM" / "Sep 10", per the brief (§5, decision 7).
6. **Org name → product name** in the meta line (§5, decision 8).
7. **Attachment chip → link.** The mock's bordered file chip renders as an `LTLink` with a leading paperclip: it opens a document, and clickable chips that navigate are links in this system (`guidelines/ltlink.md`; `guidelines/lttag.md`).
8. **"Mark all as read" is a small invisible button**, not bare header text — same optics, real control semantics.

## 7. Layout notes

- Panel: **400px wide** (side-pane scale, README §2) · height `calc(100vh − bar − 8px − 16px)` `[proposed offsets; bar token TBD in topbar.md]` · `canvas.overlay` surface · 8px radius · `floating/*` shadow `[tier proposed: floating-small]`.
- Padding: 16px panel sides; header `16px 16px 8px`; rows `12px 16px` with a 12px avatar-to-text gap; slots 8px above; meta 4px under the title. All multiples of 4 (README §2).
- Avatar 32px (`LTAvatar` XLARGE — the top bar's own avatar size). Title clamps at two lines; attachment and object names end-truncate with tooltips.
- Row separators: `LTDivider`, none after the last row; terminal row centred, muted.
- The dot column is fixed-width so read rows and unread rows keep identical text wrapping `[proposed]`.
- Badge on the bell: top-right of the icon button, `LTNotificationIndicator` counter geometry TBD → `ltnotificationindicator--counter-indicator`.

## 8. Open questions

1. **`LTAnchoredOverlay` mechanics.** No documented prop takes the anchor's icon, the overlay body, or the outside-bottom side. Extract once from `ltanchoredoverlay--icon-button-anchor` and `--custom-component-anchor`: how the Bell glyph is supplied, how children render, which prop carries `Side`, and what it ships of the dismiss/focus contract in §3.2 (`primer-dos-donts/popover.md` is the cautionary tale). Everything in §3.1–3.2 marked TBD resolves here.
2. **Who renders the badge — `counterValue` or a composed `LTNotificationIndicator`?** Both exist. Check whether `counterValue` on an iconButton anchor renders the top-right corner badge the brief asks for (`ltanchoredoverlay--button-anchor-with-counter` shows the button-anchor form), whether it hides at zero/null, and whether it caps ("99+"?). If it renders inline instead of cornered, compose the indicator (`maxCount` default 99) over an LTIconButton as the custom anchor.
3. **`navs` item shape.** Labels, counters, and whether the active tab's counter changes scheme — `ltunderlinenav--with-counters` (and `--loading-counters` for the skeleton while counts load).
4. **System rows.** `mock-data.md`: avatars are always initials, never an image — but "HyperExecute job failed" has no human whose initials apply. Proposal: system rows lead with the **Status component glyph** (Retro Glitch, the same 16px icons every status already uses, `bg?=Yes`, centred in the 32px slot) — it satisfies "every status renders with an icon" and marks the row as non-human at a glance. Alternatives: the `lambdatest-mark` from `assets/icons/` (collides with the never-an-image rule as written), or a literal `S` avatar (reads as a person named S). Needs Rajat's call, and a `mock-data.md` note either way.
5. **Deep-link destinations per event type.** Row click navigates to "the entity" — job page, run page, build screenshots, project — but the URL map is per-product work. Until it lands, no row ships without an `href`.
6. **Per-row mark-as-read (and unread).** V1 reads on open only (§5, decision 10). If triage-without-visiting turns out to matter, the control must be a real ≥24px target — likely a row-hover icon button — and it drags a "mark as unread" counterpart with it. Decide from usage, not upfront.
7. **Padding in the short formats — resolved (11 Sep 2026).** The brief's examples govern: unpadded `2:34 PM`, `Sep 2`, as a panel-local exception with no `mock-data.md` change (§5, decision 7).
8. **The event catalog.** §1.2 is a seed. Each product team owns which events notify, whom they address (owner? watcher? actor's team?), coalescing of bursts ("12 screenshots approved" as one row, not twelve), and whether any events beyond invites/shares carry actions. Coalescing rules especially — an org's CI can generate hundreds of events an hour, and an unbatched feed buries the invite that needed an answer.
9. **Announcements vs. notifications.** Three product bars already carry an announcements icon button (`topbar.md`). Two decisions: its glyph must not read as a bell (adjacent icon buttons differ by icon, `guidelines/lticonbutton.md` — name a megaphone-intent glyph in `icons.md`), and longer-term, does announcements fold into this panel as a system-authored feed, or stay a separate surface? V1: separate, untouched.
10. **Live transport.** Badge and feed update in real time (§3.1, §3.5) — websocket, SSE or polling is backend's call; the pattern only requires that the badge is fresh without a reload and that arrivals while open insert without jank.
11. **Does `LTNotificationIndicator` hide itself at `count={0}`?** The badge must vanish at zero (§3.1); whether that's component behaviour or caller logic — `ltnotificationindicator--counter-indicator`.
